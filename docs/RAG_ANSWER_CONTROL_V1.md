# RAG 回答控制 V1

> 状态：V1.1 通用修复已在本地完成，尚未重新部署；第二轮真实 DeepSeek 18 题评测仍为历史结果 12/18，第三轮待用户另行授权
> 日期：2026-08-04

## 1. 为什么增加这一层

R4 首轮真实回答虽然能正确检索资料，但仍出现时间判断错误、引入无关案例、遗漏关键区分和证据不足时继续推断。继续为每一道失败题修改提示词，会把维护成本变成“问题越多、补丁越多”。

本轮改为三个可复用对象：

```text
Claim：每条资料明确“能支持什么、不能推出什么、对应什么时间”
AnswerPlan：每次提问自动决定本题允许用哪些 Claim、最多能说到哪里
AnswerValidation：回答生成后检查数字、时间、案例与结论是否越界
```

它们是内部结构，不向普通用户展示专业字段。

## 2. Claim V1

现有 135 个 chunk 都已通过人工资料审核且每条本身是聚焦片段。首版因此采用保守的一对一规则：**一个 chunk 生成一个 Claim**，不调用外部模型重新拆写事实。

每个 Claim 包含唯一标识、原片段事实陈述、来源角色、资料时间、案例关系、可支持范围、不可外推边界、必要区分和主题。`npm run knowledge:claims` 可从已批准的 chunk、来源元数据、文化标注与案例记录重新生成全部 Claim。构建脚本强制检查版本、唯一性、案例引用、来源角色、时间和数组字段；当前为 135 个 chunk、135 个 Claim。首个必要区分规则会明确区分顾客投诉奖励、员工委屈奖励和法院判决赔偿，避免金额跨用途替代。

这不是“135 条事实永远只能有 135 个 Claim”。未来片段变复杂时可升级为一条 chunk 多个原子 Claim，但必须另做迁移和评测，不能静默改变现有事实。

## 3. AnswerPlan V1

每次问题完成 Query 改写和 BM25 检索后，系统动态生成 AnswerPlan：当前日期、问题时间、回答轨道、可回答程度、允许的 Claim、禁止混入的案例、必须分清的边界、缺少的信息和结论上限。

V1.1 保留原 Top-5 BM25 作为检索评测口径，同时让回答规划层在同一安全过滤后的 Top-12 候选中选出最多 5 条 Claim。选择依据是问题与 Claim 的文字相关度、原检索分数和通用证据意图，例如机制问题优先制度、手册、轮值和治理资料，争议问题优先边界、责任和纠错资料。这不是为某一道题写死答案，也不会让案例资料绕过原有轨道隔离。

一般文化题不会把具体案例 Claim 当成通用证明，除非用户明确问该案例或要求举事件例子；事件题只允许同一案例的 Claim。资料不足题的允许事实列表为空。

## 4. AnswerValidation V1

模型首稿不会立即发给浏览器，而是先在服务端完成通用检查：

1. 回答是否为空；
2. 资料不足时是否直接承认不足、是否仍长篇延伸；
3. 回答中的事实数字是否存在于问题、北京时间当前日期、资料日期、来源标题或允许事实；列表编号不按事实数字处理；
4. 是否引入未允许的已知案例；
5. 是否把当前年份误说成未来；
6. 二选一、真假或能力判断是否出现无依据的绝对结论；“不能说已经证明”等明确否定语境不再误报；
7. 非终局案例是否使用无依据的终局话术。

第一次未通过时，系统把具体违规原因交给模型重写一次；第二次仍未通过时，如果本题有允许 Claim，就返回排名最高 Claim 的最小可答事实并停止外推；只有真正没有资料时才只说明资料不足。只有验证通过或完成安全降级后，正文与来源才以原有 SSE 协议发送给网页。

校验器只处理可确定的边界，不声称能够自动理解所有语义。文化解释是否自然、公平、有帮助，仍需 R4 真实问题评测和用户验收。

## 5. 新运行链路

```text
Query
→ Query 改写与案例路由
→ BM25 Top-5 检索（固定评测口径不变）
→ 同一安全候选池扩至 Top-12
→ 按问题意图选出最多 5 条 Claims
→ 生成 AnswerPlan
→ 组装稳定回答提示词
→ DeepSeek 生成首稿
→ AnswerValidation
   ├─ 通过：返回回答
   └─ 不通过：重写一次 → 再检查 → 必要时安全降级
```
