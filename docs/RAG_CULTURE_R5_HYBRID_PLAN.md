# R5 关键词与向量混合检索实施说明

**状态：** 已启动；本地实验，不替换 Worker，不部署。

## 1. 为什么先不购买向量数据库

知识库共有 135 个片段，但案例轨和受限资料必须继续由现有规则锁定。按当前一般检索许可范围，首轮只需要为 96 个片段生成向量。这个规模可以把文档向量保存在项目内的只读索引中，查询时仅生成一条问题向量并在内存计算余弦相似度，无需先购买或维护完整向量数据库。

首选腾讯云 TokenHub 的 `kinfra-text-embedding-0.6b`：国内接口、OpenAI Embeddings 兼容、1024 维，当前项目可直接使用原生 `fetch`，不增加运行依赖。DeepSeek 继续负责回答生成；向量模型与回答模型可以来自不同服务。

## 2. R5 不会改变哪些边界

向量召回不能绕过以下规则：

1. 只有现有一般检索允许的 `approved` 和非案例 `limited` 片段进入向量候选；
2. 明确案例仍由 `caseId` 路由，向量不参与案例轨；
3. 系统已识别为资料不足的问题直接返回资料不足，不调用向量；
4. 回答用途过滤同时作用于 BM25 和向量候选；
5. 当前 BM25 继续是默认检索，R5 实验不会自动进入线上服务。

## 3. 实验步骤

1. 冻结当前 54/54 BM25 结果作为控制组；
2. 使用审核后的片段文本、事实字段和 `culture-v1` 生成文档向量；
3. 查询时分别取得 BM25 排名与向量排名；
4. 使用 RRF 做排名融合，避免直接比较两种不同量纲的分数；
5. 先用同一 54 题检查零回归，尤其检查案例、禁用片段、终局和资料不足；
6. 再建立一套未参与规则调试的语义改写题，判断向量是否真的带来新增召回；
7. 两道门槛都通过后，才讨论接入本地 Worker，并由用户另行决定是否部署。

## 4. 当前阻塞与用户操作

代码不会保存或输出密钥。实际生成向量前，需要用户在腾讯云 TokenHub 开通服务并创建 API Key，然后只把 Key 放入本地环境变量 `TENCENT_TOKENHUB_API_KEY`。不要把真实 Key 粘贴到聊天、代码、`.dev.vars.example` 或 Git。

得到密钥后运行：

```powershell
npm run rag:vectorize:r5
npm run rag:evaluate:r5
```

生成的实验报告为 `docs/RAG_CULTURE_R5_HYBRID_EXPERIMENT.md`。若出现任何严重回归，保持 Worker 使用 BM25，并调整融合方案，而不是修改评测答案。
