# R5 关键词与向量混合检索实施说明

**状态：** R5A 安全对照已通过；R5B 31 道冻结语义影子题首次真实对照已完成，BM25 17/31、混合检索 19/31、新增 2、回归 0。下一步进入 R5C 通用架构实验；暂不替换 Worker，不部署。

## 1. 为什么先不购买向量数据库

知识库共有 135 个片段，全部生成向量并保存在同一只读索引中。其中 96 个符合当前一般检索范围；另外 39 个是绑定具体案例的 `limited` 片段，只保留在索引中供对应案例范围使用，不能进入普通文化检索。这个规模可以在查询时直接在内存计算余弦相似度，无需先购买或维护完整向量数据库。

首选腾讯云 TokenHub 的 `kinfra-text-embedding-0.6b`：国内接口、OpenAI Embeddings 兼容、1024 维，当前项目可直接使用原生 `fetch`，不增加运行依赖。DeepSeek 继续负责回答生成；向量模型与回答模型可以来自不同服务。

## 2. R5 不会改变哪些边界

向量召回不能绕过以下规则：

1. 135 个片段都可生成向量，但普通检索只能使用现有规则允许的 96 个候选；案例受限片段必须继续匹配对应 `caseId`；
2. 明确案例仍由 `caseId` 路由，向量不参与案例轨；
3. 系统已识别为资料不足的问题直接返回资料不足，不调用向量；
4. 回答用途过滤同时作用于 BM25 和向量候选；
5. 当前 BM25 继续是默认检索，R5 实验不会自动进入线上服务。

## 3. 实验步骤

1. 冻结当前 54/54 BM25 结果作为控制组；
2. 使用审核后的片段文本、事实字段和 `culture-v1` 生成文档向量；
3. 查询时分别取得 BM25 排名与向量排名；
4. 使用 RRF 做排名融合，避免直接比较两种不同量纲的分数；
5. 先用同一 54 题检查零回归，尤其检查案例、禁用片段、终局和资料不足；
6. 再建立一套未参与规则调试的语义改写题，判断向量是否真的带来新增召回；
7. 两道门槛都通过后，才讨论接入本地 Worker，并由用户另行决定是否部署。

## 4. 当前结果与下一步

用户已在腾讯云 TokenHub 创建 API Key，并以 `TokenHub_Key` 保存到本地环境变量；代码兼容该名称，也不会保存或输出密钥。135 个文档向量已经生成，固定 54 题在第二轮达到 54/54、回归 0、严重回归 0。

可重复运行：

```powershell
npm run rag:vectorize:r5
npm run rag:evaluate:r5
```

R5A 安全报告为 `docs/RAG_CULTURE_R5_HYBRID_EXPERIMENT.md`，R5B 影子评测见 `docs/RAG_CULTURE_R5_SEMANTIC_SHADOW_V1.md`。R5B 已证明向量存在新增语义召回，但总体仅从 17/31 升至 19/31，案例路由仍为 3/5。下一步 R5C 只实验置信度感知融合、语义案例路由和自然终局意图归一化；每次同时重跑固定 54 题与冻结 31 题，在双门槛通过前 Worker 继续使用 BM25。
